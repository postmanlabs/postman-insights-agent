Funnel interpretation

Bars are ordered by when the agent actually emits each one, not by an idealized pipeline, and mix two data sources -- read the marker before comparing bars:

  • ● stage — discovered / eligible / configured: a live snapshot read off each target's current_stage/transitions. Reflects the fleet's current state, not "ever happened."
  • ◆ event — service resolved / apidump started / capture started: none of these is a coverage stage a target record can hold, so they're counted from events-type counter rows instead (distinct target IDs that ever emitted the event, within the currently retained window). apidump started intentionally ignores the target's own CoverageApidumpStarted transition, which fires synchronously right after handing the pod to StartApiDumpProcess and always "succeeds" regardless of what the background capture goroutine does — see D15 in the events matrix.
  • ▲ liveness — producing traffic: derived from last_message_at, not a discrete event.

eligible and service resolved are Discovery Mode only — they read 0 in Workspace Mode by design (there is no filter to evaluate), not because targets are being dropped. There is no capturing/uploading coverage stage in the current schema (removed in favor of liveness timestamps); "uploaded" state is derived from last_upload_at/last_upload_status. Packet-level interval counters were retired (R3); capture liveness is a timestamp, not a count.
